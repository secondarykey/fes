# 問い合わせ・やり取りの管理（CRM 的な機能、構想）

2026-10-10 時点の構想メモ。すぐに実装する予定は無く、案として考えている段階。
出店者・アーティストのマスタ化（[event-master.md](event-master.md)）を前提にする。

## 目的

店舗情報に限らず、出店者・アーティスト・一般の人とのやり取りを ID で管理し、チャットのようにやり取りできるようにする。
今はフォームやメールに散らばっているやり取りを、相手（店舗・アーティスト）や開催と結びつけて残す。

## データ

| 種類（Datastore の kind 案） | 内容 |
|---|---|
| `Thread` | ID、件名、種類（出店・出演・一般の問い合わせ・取材など）、状態（未対応・対応中・完了）、担当者、関係する `Shop` / `Artist` / `Event` |
| `Message` | どのスレッドか、送った人（スタッフか相手か）、本文、添付、日時、既読 |

- 店舗・アーティストとは ID でつながる。店舗の画面から「この店とのやり取り」を一覧で見られる。
- 相手の連絡先（メールアドレスなど）は、`ShopPrivate` と同じく非公開の情報として扱う。

## 入り口

| 相手 | 場所 | 本人の確認 | できること |
|---|---|---|---|
| スタッフ | 管理画面（`/manage/`） | 今の管理者ログイン | 全スレッドの一覧・返信・状態の変更・担当の割り当て |
| 店主・アーティスト | 店主の画面（仮に `/store/`） | Google ログイン（[event-master.md](event-master.md) の紐づけ） | 自分のスレッドの閲覧・返信・新規作成 |
| 一般の人 | 公開サイトのフォーム | ログインなし | 問い合わせの送信。返信はスレッド専用の推測できない URL で見る |

一般の人には推測できない URL（スレッド専用の長い ID つき）を渡すことで、別のログインの仕組みを作らずに済ませる。URL を知っている人は誰でも見られるので、有効期限を付ける。

## 決めること

1. **メール通知の手段**（最も大きい決めごと）
   - チャットのようにやり取りするなら、「返信が来た」ことを相手に知らせる手段がほぼ必須。
   - GAE には標準のメール送信が無い。外部のメール送信サービスを使うか、主催者の Google Workspace / Gmail から Gmail API で送るか。Google を使っている今の体制なら後者が自然。
   - 一般の人に返信の URL を届けるのにも、メールが要る。
2. **店主のログインできる期間との関係**
   - 店主のログインを「イベントの期間だけ」にすると、開催前後の問い合わせができない。
   - スレッドだけは期間外も見られるようにするか、期間外はメールでやり取りするか。
3. **迷惑投稿の対策**: 一般のフォームには、送信回数の制限や確認の仕組みが要る。
4. **保存期間**: 問い合わせの本文やメールアドレスを、いつまで残すか（非公開情報の削除と合わせて決める）。
5. **作るか、既存のものを使うか**: 本格的な CRM は大きな作業になる。全部を作らず、足りない部分だけ作る。

## 進め方（案）

1. **店主と主催者のスレッド**: マスタと店主のログインがあれば最小限で始められる。一般の問い合わせは今の方法（フォームとメール）のまま。
2. **メール通知**: 送信の手段を決めて、返信が来たことを知らせる。
3. **一般の問い合わせ**: 公開サイトのフォームと、推測できない URL での返信の閲覧。
4. **アーティスト**: 出演の連絡（出演時間、機材など）もスレッドで扱う。
