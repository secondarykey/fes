# 出店者・アーティストのマスタ化（構想）

2026-10-10 時点の構想メモ。すぐに実装する予定は無く、案として考えている段階。

## 背景

- 今の FES には出店者・アーティスト専用のデータが無い。サイトでは汎用のページ（`Page` のツリー）として、会場マップでは対応表（`maps/data/<開催>/shops.tsv`）として、開催ごとに作り直している。
- 出店者の情報は Google フォームの申込が元で、表記ゆれ・主催者向けの回答・掲載の同意など、毎回人が判断している（[maps-automation.md](maps-automation.md)）。
- 同じ出店者・アーティストが毎回のように参加するが、前回の情報を引き継げない。

## 考え方

開催をまたいで変わらない「出店者・アーティスト」と、開催ごとに変わる「参加（番号・区画・その回のメニューや出演枠）」を分けて持つ。

| 種類（Datastore の kind 案） | 内容 | 開催をまたぐか |
|---|---|---|
| `Event` | 開催（例: `2026-autumn`）。日程、マップ画像、GPS 基準点 | — |
| `Shop` | 出店者。店名、カテゴリ、紹介文、リンク（Instagram など）、写真、掲載の同意、店主のメールアドレス | またぐ |
| `ShopPrivate` | 出店者の非公開情報。電話番号、住所、許可証・保険の有無 | またぐ |
| `Entry` | 出店者の参加。開催、出店番号、区画（マップのタップ範囲）、その回のメニュー、状態（申込・採用・不採用・取消） | 開催ごと |
| `Artist` | アーティスト。名前、紹介文、リンク、写真 | またぐ |
| `Performance` | 出演。開催、ステージ、開始・終了時刻 | 開催ごと |

- 公開情報と非公開情報は kind を分ける（`Page` / `PageData` と同じ考え方）。公開側の処理で非公開情報を読み込まないようにし、管理者と本人だけが読めるようにする。
- 今の申込 CSV・写真 ZIP は、取り込み機能で `Shop` / `ShopPrivate` / `Entry` に入れる（`maps/tools/shops` と `maps/tools/images` の処理を移す）。

## マスタ化でできること

### 会場マップ

- 店舗データ（`shops.json`）をマスタから生成できる。対応表・申込 CSV・書き起こしが不要になる。
- マップのデータを API（例: `/maps/data.json`、キャッシュつき）から配信すれば、店舗情報の修正に再デプロイが要らなくなる。
- 出演枠があれば、ステージをタップしたときに「今の出演」「次の出演」を出せる。
- カテゴリで絞り込む、店名で探す、などの機能が作れる。

### 公開サイト

- 出店者一覧・アーティスト一覧・タイムテーブルのページを、テンプレートでマスタから生成できる。手でページを作らなくてよくなる。
- 店舗ページとマップを相互にリンクできる（ブースに QR コードを置いて店舗ページに飛ばす、など）。
- 開催ごとのアーカイブに、その回の出店者・出演者の一覧を残せる。

### 運営

- 2 回目以降の出店者は前回の情報を引き継げる（申込のたびに全部入力し直さなくてよい）。
- 申込の状態管理（採用・不採用・取消）と番号の割り振りを管理画面で行える。
- 出店者への一斉連絡（搬入時間、区画図、当日の注意）の宛先をマスタから作れる。
- 開催後に非公開情報（電話番号・住所）を消す、といった個人情報の扱いを決めて実装できる。

## 店主が自分で店舗情報を直す仕組み

### ログイン

- 今の管理画面と同じ Google ログイン（GIS、ID トークンを `/session` で検証）を使う。別のログインの仕組みは作らないので、**店主は Google アカウントが必要**という前提にする。
- 管理者とは別の役割（店主）にする。`Shop` に店主のメールアドレスを持たせ、ログインしたメールアドレス（`email_verified`）と一致する店舗だけを編集できる。管理者の判定（`Site.Managers`）と同じくフェイルクローズにする。
- 店主の登録は、申込のメールアドレスを管理者が `Shop` に設定する。
- **ログインできるのはイベントの期間だけ**にする。`Event` に店主がログインできる期間（開始・終了）を持たせ、期間外はログインもセッションの継続もできないようにする。期間外は既存のセッションも無効として扱う。
- 店主の画面は管理画面（`/manage/`）とは別にする（仮に `/store/`。URL は別途決める）。店主は管理画面にはログインしない。CSRF 対策は管理画面と同じ方式にする。

### 編集できる範囲

| 項目 | 店主 | 管理者 |
|---|---|---|
| 店名、紹介文、リンク、写真、掲載の同意 | 編集できる | 編集できる |
| その回のメニュー | 締め切りまで編集できる | 編集できる |
| 電話番号・住所など（非公開） | 自分の分だけ閲覧・編集できる | 閲覧・編集できる |
| 出店番号、区画、カテゴリ、状態 | 閲覧のみ | 編集できる |

### 公開までの流れ

- 店主の編集は、すぐには公開しない。下書き（ページの `Draft` と同じ考え方）として保存し、管理者が確認して公開する。公開済みの内容と変更点を並べて見られるようにする。
- ログインできる期間とは別に、編集の締め切り（その回のメニューなど）を設けられるようにする。

### 写真

- アップロード時にサーバーで向きの補正（EXIF）、縮小、形式の変換を行う。今回手作業だった処理がいらなくなる。
- GAE の標準環境では cgo が使えない前提で考える（webp の変換ライブラリが cgo のため）。純粋な Go で縮小して JPEG で保存するか、変換だけ別のサービス（Cloud Run など）に任せる。
- 掲載の同意が無い写真は公開しない。

## 進め方（案）

1. **マスタと取り込み**: `Shop` / `ShopPrivate` / `Entry` と、申込 CSV・写真 ZIP の取り込みを管理画面に作る。マップの `shops.json` をマスタから生成する。
2. **店主の編集**: 店主のログインと編集画面、下書きと承認の流れを作る。
3. **アーティストとタイムテーブル**: `Artist` / `Performance` と、サイトのページ生成、マップの「今の出演」。
4. **申込フォームの置き換え**: Google フォームをやめて、FES 上で申込を受け付ける（同意の取得、写真のアップロード、2 回目以降の引き継ぎ）。

## 決まっていること

- すぐには実装しない（案の段階）
- 店主のログインは Google アカウントのみ。別のログインの仕組みは作らない
- 店主がログインできるのはイベントの期間だけ（期間外はログインできない）
- 店主の画面は管理画面とは別の URL にする

## 決めること

- 店主の画面の URL
- ログインできる期間の長さ（申込から開催後のいつまでか）
- 店主の編集を承認制にするか、即時公開＋事後確認にするか
- 非公開情報を開催後にいつ消すか
- 出店者・アーティストを同じ仕組み（「参加者」）にまとめるか、別々にするか
